# Logo 设计

让所有者在少数几轮评审里得到一个有表达、小尺寸可识别、能自己接手微调的标志，并把它整理成可重复导出的多平台资产。Agent 负责调研、出方向、把模糊反馈翻译成几何问题和规范化导出；造型的最后手感由所有者在矢量工具里定。

## 任务边界

- 新 Logo：从简报开始，走完整流程。
- 下一轮：读上一轮的交付与反馈，只做反馈要求的范围。所有者已选定方向后，不再扩展新概念。
- 定稿导出：所有者已有手调母版时，只做规范、导出和校验，**不改母版的任何路径**。
- 只要求小改（换色、导出一个尺寸）时直接做，不套完整流程。

可以自己执行每一轮，也可以写成工作单派给执行者；派单时用 [每轮工作单模板](references/round-order-template.md)。

## 流程

### 0. 简报

动手前收集并写下来，缺项能推断的自己补，影响方向的才问：

- 产品名的来历和含义、一句话定位、目标平台（macOS 应用与菜单栏、iOS、Android、Web 等）。
- **所有者已有产品的 Logo 造型与主色清单**。新方向要避开它们，否则所有者会一眼认出撞脸。
- 使用场景，见下一节。
- 所有者给的情绪板、喜欢和讨厌的标志。只吸收风格，不照搬其中任何一个现有 Logo。
- 仓库是否公开：公开时，竞品截图和参考图放在仓库外，仓库里只写文字归纳和链接。

### 使用场景

场景决定调研看什么、标志主要以什么形态出现、每轮必须检查哪些尺寸。简报里写明主场景和次场景，不需要的平台不做。各场景的尺寸见 [平台规范](references/platform-specs.md)。

| 场景 | 调研对象 | 标志的主要形态 | 每轮必看 |
|---|---|---|---|
| Web 与 PWA | 同领域网站和开发者工具的页头标志、浏览器标签页图标 | 符号加字标的横版组合标；单独的符号用于 favicon 和安装图标 | 页头 24–32px 高的组合标、浏览器标签页 16/32px、浅色和深色主题、PWA 安装图标（含 maskable 安全区） |
| 移动应用（商店） | 商店里同类应用的真实图标 | 满版方形图标 | 商店尺寸、桌面图标尺寸、系统遮罩 |
| 桌面应用 | 同类桌面应用的图标和菜单栏图标 | 应用图标加菜单栏 template | 应用图标各尺寸、菜单栏 1x/2x 浅深背景 |

Web 场景里，用户最常看到的是页头的组合标和标签页里 16px 的符号，所以符号必须在 16px 下靠剪影成立，字标要和符号的笔画粗细、圆角协调。按大尺寸定的缝隙宽度（例如 128 单位画布上的 4 单位）缩到 16px 只剩 0.5px，交叠表达的含义会整个丢失，因此 R01 就要同时出 16px 的简化版本，而不是等定稿再补。

### 1. 调研与发散（R01）

1. 按场景看同类产品的**真实标志**，归纳共性（构图、主体占比、底色、厚重感）和差异化空间，写进本轮 README。
2. 列出撞脸风险：知名同类标志、平台里已有的相似形象，并在每个方向旁写明差异。
3. 出 3–4 个方向。每个方向一句话说明它表达什么。

方向要有**表达**：有性格的形象剪影（单色粗剪影配少量负形带出神态）通常比字母和符号的简单拼合更有记忆点。字母融合可以做，但不能为了融合而融合。也不要画成线性 UI 小图标，或死磕产品名里的具象物件。

### 2. 每轮交付

每一轮都交同一套东西，放在 `rounds/R<nn>-<日期>/`：

- **可编辑源 SVG**：手写或程序生成的干净路径，不描摹位图；分组和命名有意义；会被分别调整的部件（例如头、身体、爪）保存为独立路径，方便所有者导入矢量工具接手。
- **多尺寸检查图**：1024、128、32、16，加上场景表里“每轮必看”的项目；主色版加单色版。Web 场景还要把组合标和 favicon 放进模拟的页头和浏览器标签页里看。
- **汇总页** `index.html`：所有方向和尺寸放在一页对比。
- **README**：记录上一轮的反馈原话、本轮做了什么、各方向的理由和撞脸差异。保留历史轮次，不覆盖。
- **简短推荐**：最推荐哪个、为什么，几行就够。

小尺寸不可读的细节（瞳孔、趾缝、细胡须）要么在小尺寸下去掉，要么做光学加粗，不能指望缩放后还看得见。

### 3. 评审与精修

所有者选出方向后进入精修轮。所有者的反馈常是感受（“线条不流畅”“衔接生硬”），先把它**翻译成具体几何问题**再改：

- 定位到具体路径段：哪里是直线混进了曲线、哪里两个形体贴边相切糊在一起、哪里出现尖刺或凹尖角。
- 曲线交接做到相切；关键轮廓做到曲率连续（G2），不出现生硬的弧直相接。
- 前后层次用**统一宽度的负形缝隙**分开，宽度按最小尺寸的可见度确定。
- 凹角、凸角的圆角各自成体系，在 README 写明取值，不留零散数值。

精修轮出**受控变体**：A1 只改问题一，A2 只改问题二，A3 合并。另附一张原稿与各变体半透明叠图，以及交接处的大尺寸局部放大，让所有者看清每个改动的单独效果。

比例参考（黄金比例等）只作参考，不要为了凑比例做程序盲搜或硬改造型。

### 4. 所有者手调母版

所有者把选中的变体导入 pen.dev、Figma 等矢量工具亲手微调，保存为**编辑母版**。从此：

- 母版是唯一可编辑源，造型以母版为准。旧轮次的 SVG、规则和推荐都只是历史记录。
- Agent 不再改母版里的路径；发现问题时提出建议，由所有者决定。

### 5. 定稿规范与导出

按目标平台写规范，并用脚本从母版生成全部导出物。平台尺寸和安全区见 [平台规范](references/platform-specs.md)，动手前按平台官方模板核对当前版本。

- **规范写进品牌目录的 README**：画布、主体形状与边距、标志高度和视觉中心、主色与墨色、各平台变体（例如菜单栏模板去掉瞳孔）。数值先给所有者确认。
- **导出脚本**：读母版（不修改它）→ 生成应用图标各尺寸、平台模板、紧贴边界的单色和反白 SVG → 写一份含 SHA-256 的清单。依赖装在仓库外；同一母版和依赖下重复导出应逐字节一致。
- **`--check` 模式**：不写文件，检查导出物是否过期、缺失或被手改，以及透明边距、模板只含黑与透明等硬约束。
- 镂空用真实的布尔减去，不要用和背景同色的描边伪装，导出到不同背景或渐变时会露馅。
- 写一份 `rounds/FINAL-<日期>.md`，记录从 R01 到定稿每轮的评审意见和结果。

## 验证与交付

每轮交付前自己看一遍渲染结果，不只看源码：16px 和菜单栏尺寸是否还能认出、单色版是否成立、浅深背景下是否都清楚。用脚本检查的项目（尺寸、边距、颜色、哈希）和人工看过的项目分开报告；没看过的不写成通过。

交付时告诉所有者：本轮看哪个文件（通常是 `index.html`）、推荐哪个、需要他们决定什么。评审轮不合并，定稿后再合并。
