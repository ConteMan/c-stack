# 按读者任务组织文档

新写或用户要求重组时阅读本文件。下面是内容选择依据，不是每篇都要填满的模板；已有结构合适时沿用。

## 所有类型先确定的内容

读者是谁，要理解什么、完成什么操作或作出什么决定？哪些是已知事实，哪些是目标或尚未确定的设计？只展开与该任务相关的信息。

## README

让第一次接触项目的人判断用途并完成第一次成功使用。按需要覆盖用途和限制、必要前提、最小操作示例、成功结果，以及更深文档的入口。

命令应来自项目材料或实际验证。缺少成功输出时说明如何确认，不编造日志行。不要把完整架构、运维手册和路线图都塞进首页。

## 设计文档与技术方案

让读者判断方案是否满足目标，并理解系统职责与取舍。按需要覆盖问题与目标、范围和非目标、约束、系统边界、关键行为、数据语义、失败与降级、方案取舍、演进和验证方式。

区分当前行为与拟议行为。涉及并发、缓存、版本切换或重试时，优先说明读者需要理解的不变量、触发条件、可观察结果和失败边界。未确定的事项明确保留为问题，不默认设计已经闭合。

## API 与跨端契约

让调用者明确何时调用、输入是什么、响应代表什么、失败后怎么做。按需要覆盖认证、参数与字段含义、默认与空值语义、错误分类、幂等与重试、兼容性和示例。

字段名、类型、状态码和协议术语不为了语言统一而改写。实现细节只在影响调用者决定时进入契约。示例明确是示例，不能暗示未保证的行为。

## 操作手册、排障与迁移指南

让操作者确认适用场景，按正确顺序执行，并判断结果。按需要覆盖前提与权限、必要备份、风险、条件分支、步骤、验证、停止条件和有依据的恢复路径。

区分人执行的动作与系统自动行为。若恢复路径未验证，明确写出限制；不能因为有备份就保证可以回滚。排障按症状与可观察证据推进，不把猜测的根因写成事实。

## 技术决策记录

让后来的维护者理解为什么选择该方案、适用边界和代价。按需要覆盖状态与日期、背景、决策、关键备选、理由和后果。保留被接受的风险；不把决策说明改成只讲优点的宣传。

## PR 描述、提交说明和发布说明

让读者理解具体触发场景、改后行为、兼容性影响和实际验证。按变更复杂度调整长度，写最终改动，不堆砌过程记录。技术发布说明说明升级动作和不兼容处；宣传语气由作者决定。

## 注释、错误信息与界面帮助

注释优先解释非显然的约束和原因，避免复述代码。错误信息描述发生了什么，能确定时给出可执行的下一步；不能确认原因时，不断言原因。界面帮助只保留影响用户操作的信息，不把内部实现细节塞进产品流程。

## 技术博客与解释文章

技术部分保持事实与指代清楚；必要的比喻后接准确说明。尊重叙事顺序、作者语气和概念铺垫，不把故事结构强制改成每段结论先行。
