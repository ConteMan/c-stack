# 保真改写示例

以下都是构造的短例。例子中的事实只属于对应输入，不是其他文档可以直接填入的默认值。

## 推荐不能改成强制

原文：上线前最好跑一下回归测试。

可改：建议上线前运行回归测试。

规范性文档采用“应／宜”约定时：上线前宜运行回归测试。

不能仅为统一词表改成“应”或“必须”。作者明确把要求升级为强制时，才作业务规则变更。

英文原文：You should run the regression tests before deployment.

可改：Before deployment, you should run the regression tests.

也可以直接保留原句。不能把 `should` 改成 `must`。

## 条件范围与时序不能丢

原文：仅当主节点不可用且副本已追平时，系统才切换；切换完成后再恢复写入。

可改：主节点不可用且副本已追平时，系统才切换。切换完成后，系统恢复写入。

不可改：主节点不可用时，系统切换并恢复写入。

错误同时丢掉副本追平条件和恢复写入的前提。

## 并列事实不能自动改成因果

原文：锁超时是 30 秒。任务最长运行 20 秒。

可改：保留两句。

需要解释取值依据时，向作者确认：30 秒是否根据任务上限和额外余量确定？未确认前不加“所以”。

## 主体未知时不要猜

原文：请求失败后会重试。

可改：请求失败后会重试。

向作者确认：重试由客户端、网关还是服务执行？次数和适用错误是什么？

不可改：客户端会重试 3 次。它同时编造了执行者和次数。

## 性能声明不补造数字

原文：缓存调整后，性能明显提升。

可改：缓存调整后，性能提升。

交付说明：原文未提供指标、测量值与条件；改写保留了作者的定性结论，未核实效果。

如果“明显”指的是有定义的测量等级，先保留或确认等级，不按禁词表删除。不能补造 p99、QPS、机器型号或日期。

## 统计术语与多领域概念可以保留

原文：两组差异具有统计显著性。这里的“节点”包含集群节点和树节点。

不要把“显著性”当成宣传词删除。两种节点使用清楚的限定即可，无需强行改名为“项”。如果统计结论的依据缺失，只报告证据缺口，不将其视为已经证伪。

## 未确定与部分保证不能变成承诺

原文：该补丁可能降低尾延迟，但还没有在生产环境验证。读取通常命中缓存；缓存失效时访问数据库。

可改：保留“可能”“未验证”“通常”和缓存失效分支。

不可改：该补丁降低尾延迟。读取始终命中缓存。

## 整理步骤不补造操作事实

原文：升级前备份数据库，停止服务，再升级。迁移失败时按已验证的恢复手册处理。

可改：

1. 备份数据库。
2. 停止服务。
3. 升级。
4. 如果迁移失败，按已验证的恢复手册处理。

缺少命令、手册链接与成功标志时，指出这些缺口。不要补造 `app migrate`、输出文本或“只能用备份恢复”的保证。

## 目标契约不能被当前实现替换

原文：批准的目标要求新旧客户端兼容；当前实现尚未完成兼容处理。

可改：目标要求新旧客户端兼容。当前实现尚未满足该要求。

不能根据当前代码把目标改成“不支持旧客户端”。若用户要求调整目标，应把它明确写成新的决策。
