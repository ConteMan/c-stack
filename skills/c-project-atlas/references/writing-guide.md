# 从项目材料提炼概览

首次组织内容或卡片过密时阅读。以下项目、事实、路径和日期均是虚构示例，不能作为真实项目的默认内容。

## 先建立整体，再补局部

先问读者能否回答四件事：为什么有这个项目；主要输入怎样变成可用结果；目前哪些能力可用；接下来需要谁决定什么。阅读 README 后用入口代码核对职责，用 Git 和可访问的 Issue／PR 核对状态，不按目录逐个翻译成卡片。

通常从用途、体验和边界开头，再用 `flow` 展开关键主线，最后进入「现状与决策」。按项目实际需要分区，不为了凑结构填空卡片。连线只表达证据支持的关系；“同时出现”不代表“导致”。

## 把细节藏进来源

虚构项目“纸园”的材料说明：使用本地文件保存书目，查询与借阅登记独立，先验证个人整理需求。不要添加团队规模、耗时或性能收益。

过密：

> 查询调用 CatalogReader.open()，设置只读参数，校验内部版本，持有文件锁后解码每一行记录，随后执行过滤。

更适合概览：

> 查书不会改变原书目。借阅登记通过独立操作保存。

实现细节通过 `sources: src/catalog.js:24` 留给需要深入的人。只有读取了这一位置并确认相关行为，才能把它作为来源；不能根据文件名猜测。

每张卡摘要直接说职责或结果，详情补一个必要边界。详情超过三句时先删去重复和实现参数；确实有两个主题时再拆卡。不要把一整页设计文档塞进折叠详情。

## 状态必须有证据

- `done`：例如提交已合入且测试材料支持“借阅登记可用”，不因为代码目录存在就宣布整个项目完成。
- `next`：例如 Issue 明确“下一步支持归还提醒”；Issue 是提案时写“提案，尚未批准”。没有可确认计划时写“已读材料未记录下一步”，并限定查阅范围。
- `decision`：例如决策记录于虚构的 2026-01-02 批准“先做本地书目”，原因是“先验证个人整理需求”。日志只说删去某模块时，可确认删除与提交日期；原因写“原因未记录”，不能补成“为简化维护”。
- `open`：例如文档明示“重复书目处理待定”。从材料缺口推导的问题写“推断：重复书目规则仍需确认”，不能冒充团队已立项。

不要把当前提交时间当成所有功能完成日期，也不要把最后一条修复当成下一步计划。项目概览保留对所有者有用的项目状态，不抄录 Agent 工作日志、个人日程和每次执行过程。

## 保持更新可审阅

先看 `check` 的影响映射，再读改动事实。保留卡片 ID 和顺序，修改它实际影响的摘要、详情、来源与状态；新增卡片追加，删除说明理由。若来源行号移动，及时调整；文件能读并不能证明旧行号仍指向正确事实。

用户说“这里没看懂”，先解释其批注对应概念；确认原因后改对应卡片。用户要求不支持的能力时标明需求状态，不能为了让反馈看起来“处理完”而宣称已经实现。
