# 仓库维护与评估

## 新增、扩展与迁入

一个技能应对应可辨认的任务。新增前比较已有入口：只是文档类型、技术栈或输出形式不同，通常扩展模式或引用资料即可。

新增或迁入按以下顺序推进，细节按任务规模调整：

1. 说明重复出现的任务、预期收益和不适用场景。
2. 检查已有技能是否可扩展；检查来源和公开分发条件。
3. 写短而完整的 `SKILL.md`，资料放在技能目录内并按需引用。
4. 提供正向触发、邻近但不应触发、以及易改变语义的行为用例。
5. 运行结构校验，新增脚本还要验证实际行为。
6. 在真实任务中观察结果，再决定是否扩大使用范围。

当前包含技术写作与项目概览画布；两者的模型行为仍待评估。本地其他技能尚未迁入。后续每次迁入都记录来源、必要改动、依赖、验证结果和已知限制，不把本地目录整体公开。

## 命名与成熟度

自有方法技能采用 `c-<capability>` 命名，以减少与外部技能冲突。第三方迁入不必强行改名，但需处理实际的名称冲突。

成熟度写在 README 目录表里：

- 初版：结构可加载，有评估用例，尚未积累行为证据。
- 日常使用：记录过多个真实任务结果，覆盖主要边界。
- 退役：新入口说明替代方式；删除前检查引用和安装迁移影响。

不以技能数量为目标，不用复制目录表示成熟度。

## 三类验证

| 验证 | 工具或方式 | 能证明什么 |
|---|---|---|
| 静态结构 | `make validate` | frontmatter、引用路径、资源和评估用例格式可用 |
| 工具回归 | `make test` | 链接、卸载和校验脚本遵守已测试的行为约束 |
| 模型行为 | 实际调用技能，按用例裁决 | 当次模型是否守住任务边界、语义和交付要求 |

`evals/<name>/cases.json` 是行为评估输入，不是已通过的测试结果。当前脚本只验证用例结构，不调用模型，也不计算模型准确率。

## 行为评估方法

触发用例在技能未显式选定的环境运行，观察是否被选择。行为用例明确加载该技能，提供用例的请求与输入，保留输出和模型环境。一次评估至少记录日期、skill commit、客户端、模型标识、用例 ID、实际输出、裁决理由。

按 `must_preserve` 和 `must_not` 判断含义，按 `should_improve` 判断可读性；不要求模型复现固定句子、标题或措辞。无法从运行记录观察技能选择时，把触发结果记为未验证。

技术写作行为用例优先检查：

- 推荐、强制、允许和能力没有互换。
- 条件范围、时间顺序、因果关系、否定与不确定性没有改变。
- 未知的主体、数字、命令、风险、成功标志没有被补成事实。
- 审查没有变成擅自修改；局部润色没有变成整篇重建。
- 文档类型要求的信息缺口被指出，但未把文档变成大量占位符。

语义改变直接判该用例失败。风格偏好可以有解释充分的例外，不做“达到八成”的形式评分。

## 维护记录

行为评估执行后，再提交日期化的结果记录；未执行不创建看似已完成的报告。修正规则必须来自具体任务或已观察失败，同时增加能暴露问题的用例。评估资料公开前清理个人和内部项目内容。
